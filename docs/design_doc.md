# Технический дизайн-документ: ИИ-поиск поставщиков (Direct Procurement)

Версия: 0.1 (черновик для пилота, этап 1)
Дата: 2026-08-06
Статус: draft — требует согласования с бизнес-заказчиком закупок и владельцем данных

## 1. Резюме

Задача по ТЗ — не «ИИ, который гуглит поставщиков», а система, которая
превращает текстовый запрос байера в проверяемый структурированный список
кандидатов. Ключевая архитектурная развилка: там, где JayCopilot полагается
на LLM «из головы» (отсюда галлюцинации, мёртвые компании, нестабильная
глубина), это решение строится как **пайплайн с детерминированным ядром и
LLM только на краях** — нормализация запроса и извлечение фактов из текста.
LLM никогда не является источником факта о компании; источник факта — это
реестр, сайт компании или площадка, а LLM в лучшем случае помогает его найти
или прочитать.

Главный принцип верификации: **любой кандидат либо резолвится в ИНН
(ОГРН), либо остаётся лидом**, а не поставщиком. Это закрывает три болевые
точки из ТЗ одним механизмом: прекращение деятельности, смена названия/
реорганизация, актуальность контактов — всё это факты, привязанные к ИНН, а
не к строке текста.

## 2. Из ТЗ в архитектуру: таблица трассируемости

| Требование ТЗ | Как закрывается |
|---|---|
| Поиск по РФ | Google CSE / Yandex Search API — общий веб-поиск (см. §7); pulscen.ru/optlist.ru/DuckDuckGo рассматривались и убраны, см. §7 |
| Поиск по зарубежью (Китай, Alibaba и т.п.) | Отдельный канал generate_candidates для зарубежных источников (см. §7) — не реализован в этапе 1 |
| Карточка поставщика (контакты, сводка) | Enrichment-слой, факты с указанием источника и даты |
| Весовые критерии / ранжирование | Детерминированный скоринг (§6), веса — конфиг, не хардкод |
| Отсев неактуальных / сменивших имя | Резолвинг в ИНН через `DadataEnricher` (реализовано, см. §10) + жёсткое исключение ликвидированных из выдачи в `pipeline.py` |
| Работа с реестрами (лицензии, Роспотребнадзор) | Не реализовано (§5.4) — источников данных нет; Росреестр — см. примечание ниже |
| Excel-выдача | Export-слой с полями "источник/дата/достоверность" на каждое значение |
| Сверка с ручным ресерчем, KPI | Golden set + метрики (§9) |
| «Фифти-фифти» (человек проверяет) | Флаги достоверности на уровне поля, не всей записи (§8) |
| Тиражируемость на другие категории | Слой 0 (атрибуты, бренд) работает без категорийной привязки, не требует конфига на новую категорию (§4) |

**Примечание по Росреестру.** Росреестр — реестр объектов недвижимости и
прав на них, он не предназначен для проверки юрлиц-поставщиков. Скорее
всего попал в ТЗ по инерции («реестр = проверка контрагента»). Рекомендация:
заменить на ГИР БО (bo.nalog.ru, финансовая отчётность) и ЕИС zakupki.gov.ru
(история контрактов, РНП) — они закрывают реальную потребность в проверке
надёжности. Если у Росреестра всё же есть конкретный кейс использования
(например, проверка юр. адреса на массовость через объект недвижимости),
это нужно явно сформулировать с заказчиком отдельным пунктом.

## 3. Пайплайн (по шагам)

```
Запрос байера
     │
     ▼
[1] Слой 0: атрибуты (числа+единицы), бренд (LLM, опционально)
     │  → числовые характеристики, "чистое" название товара, бренд
     ▼
[2] Генерация кандидатов (recall, широкий охват)
     │  ├─ Google CSE / Yandex Search API — общий веб-поиск, реализовано (§7)
     │  ├─ Yandex gen-search — генеративный ответ, опционально (§7)
     │  ├─ pulscen.ru/optlist.ru/DuckDuckGo — рассматривались, убраны (§7)
     │  ├─ Локальная база ЕГРЮЛ (BM25 + эмбеддинги) — не реализовано
     │  └─ зарубежные источники (Alibaba/1688/gsxt.gov.cn и т.п.) — не реализовано
     ▼
[3] Резолвинг в ИНН/ОГРН (precision)
     │  → отсев ликвидированных/банкротных/недостоверных
     │  → нерезолвленные кандидаты уходят в корзину "неподтверждённые лиды"
     ▼
[4] Обогащение фактами (по ИНН, по источникам §5)
     ▼
[5] Дедупликация и слияние карточек (несколько источников → одна компания)
     ▼
[6] Скоринг (релевантность / масштаб / надёжность)
     ▼
[7] Экспорт в Excel с полями "источник/дата/достоверность"
```

Каждый шаг — отдельный модуль с логами и метриками, чтобы можно было мерить
recall/precision по шагам, а не только итоговое качество (см. §9).

## 4. Тиражируемость: заход через конфиг категорий не оправдал себя, убран

Изначально здесь был `config/categories.yaml` — словарь "категория ->
синонимы/ОКВЭД/ТН ВЭД/реестры", по которому `query_normalizer.py`
сопоставлял запрос байера с одной из заранее описанных категорий (плюс
LLM-fallback на случай, если словарь не находил совпадения). Идея была в
том, что новая категория закупок = новая запись в конфиге, а не новый код.

На практике (design-обсуждение) при разумном числе тестовых категорий (3-4)
это почти никогда не срабатывало на реальных разнородных запросах —
`category` выходил `None`, и `okved`/`tnved`/`registries`, которые от него
зависели, оказались нигде не читаны дальше по пайплайну (dead code с самого
начала — `enrichment.py` их не использует, задел под §5.4 ниже так и не
реализован). Убрано целиком, а не доработано: `query_normalizer.py` теперь
тонкая обёртка `raw_query -> NormalizedQuery(search_terms=[raw_query])`.

Тиражируемость на новые категории закупок сейчас держится не на
курируемом человеком конфиге, а на том, что Слой 0 (`attribute_extractor.py`,
`brand_extractor.py`) работает для ЛЮБОГО запроса без категорийной
привязки — числовые атрибуты и бренд извлекаются из текста напрямую,
независимо от того, какая это товарная группа.

## 5. Источники данных

### 5.1 Ядро (обязательные)

- **ЕГРЮЛ/ЕГРИП** (открытые данные ФНС, egrul.nalog.ru) — статус компании,
  ИНН/ОГРН, юр. адрес, история наименований, правопреемство при
  реорганизации, дисквалификация руководителей.
- ~~pulscen.ru/optlist.ru~~ — рассматривались как обязательные источники,
  убраны (§7): CSS-селекторы так и остались неоткалиброванными
  PLACEHOLDER'ами с самого начала, 0 кандидатов. Источник кандидатов по
  РФ сейчас — Google CSE/Yandex Search API (§7).

### 5.2 Финансы и масштаб

- **ГИР БО** (bo.nalog.ru) — бухгалтерская отчётность, закрывает требование
  «оборот за последние ~2 года» напрямую и бесплатно.
- Численность сотрудников — открытые данные ФНС (среднесписочная
  численность) либо коммерческие агрегаторы (см. 5.5).

### 5.3 Надёжность

- **ЕИС zakupki.gov.ru** — история контрактов, реестр недобросовестных
  поставщиков (РНП).
- **КАД Арбитр** — арбитражные споры.
- **ФССП** — исполнительные производства.
- **Федресурс / ЕФРСБ** — банкротство, существенные факты.
- Налоговая задолженность — открытые данные ФНС.

### 5.4 Отраслевые реестры (по товарной группе)

Не реализовано — источников данных нет (ни у ФГИС «Реестр лицензий», ни у
Росаккредитации/Росздравнадзора нет готового бесплатного API, см. §11).
Раньше это планировалось привязать к категории закупки из конфига (§4) —
сама привязка убрана вместе с категориями, но список потенциальных
источников ниже актуален независимо от способа их подключения к пайплайну.

- Утилизация отходов → реестр лицензий Росприроднадзора (I–IV класс
  опасности).
- Лабораторные услуги → реестр аккредитованных лиц Росаккредитации
  (**с проверкой области аккредитации**, а не только факта наличия
  аккредитации), Росздравнадзор — для медицинских лабораторий.
- Прочие лицензируемые виды деятельности → ФГИС «Реестр лицензий»,
  Ростехнадзор — по необходимости.

### 5.5 Быстрый старт / зарубежье

- **Dadata** — реализовано (`enrichment.DadataEnricher`, см. §10): бесплатный
  тариф suggest API по названию организации для старта пилота, прежде чем
  вкладываться в полноценный локальный индекс ЕГРЮЛ. Есть дневной лимит
  бесплатных запросов (порядок — тысячи в день, уточнить текущий на
  dadata.ru при выходе за пилот).
- Далее, по мере роста нагрузки — Контур.Фокус / СПАРК / Seldon.Basis.
- Зарубежье: **gsxt.gov.cn** (китайский госреестр юрлиц, аналог ЕГРЮЛ),
  OpenCorporates, GLEIF (LEI). Alibaba/Made-in-China/1688 — открытого
  поискового API нет, нужен парсинг с учётом их anti-bot защиты (это на
  порядок сложнее того, что уже не удалось с pulscen/optlist/DuckDuckGo —
  см. §7 и риски в §11). Опционально:
  ImportYeti / Panjiva / ImportGenius (таможенные декларации) — сильный
  сигнал, что поставщик реально отгружает товар, а не просто зарегистрирован
  на площадке.

## 6. Скоринг

LLM не используется для оценки «надёжность от 1 до 10» — такая оценка не
воспроизводима и не объяснима. Вместо этого — детерминированная формула из
фактов плюс отдельный LLM-скор релевантности текста запроса к номенклатуре
кандидата.

| Ось | Из чего считается | Источник |
|---|---|---|
| Релевантность | пересечение токенов запроса (без чисел, со стеммингом) с текстом сниппета/сайта; отдельно — совпадение числовых атрибутов и бренда | текст карточки/сайта кандидата |
| Масштаб / серьёзность | выручка, численность сотрудников, срок существования, размер УК | ГИР БО, ФНС |
| Надёжность | наличие в РНП, банкротство, открытые исполнительные производства, налоговая задолженность, отметка о недостоверности сведений в ЕГРЮЛ | ЕИС, Федресурс, ФССП, ФНС |

Итоговый скор — не сумма, а `relevance^a × trust^b × штраф_за_неполноту`
(см. scoring.py) — весов из нормализованных (0..1) осей, конфиг —
`config/scoring_weights.yaml`, профиль на категорию поддерживается
механизмом (`weights_for_category`), но сейчас всегда используется профиль
"default" — категория закупки больше не определяется (§4).

В прототипе (см. §10) реализован только каркас формулы и релевантность по
пересечению текстовых токенов — интеграция с ЕГРЮЛ/ГИР БО/ЕИС вынесена как
`Enricher`-интерфейс, который сейчас реализован заглушкой (нет доступа к
платным API/сети из среды разработки, см. §11).

## 7. Источники кандидатов — что рассматривали, что осталось

Технически источники — генераторы **кандидатов** (шаг [2] пайплайна), не
источники истины: любой факт, полученный отсюда, вторичен по отношению к
резолвингу в ЕГРЮЛ на шаге [3]. Практическая причина: ни у одного источника
нет гарантии, что карточка компании актуальна (протухшие объявления,
компании, переставшие отвечать) — это именно та проблема, которую ТЗ просит
решить, а не унаследовать.

### 7.0 pulscen.ru/optlist.ru/DuckDuckGo — рассматривались, убраны

Изначально pulscen.ru/optlist.ru (специализированные B2B-каталоги, CSS-
селекторы + JSON-LD, `sources/base.py:CatalogSource`) были обязательными
источниками по ТЗ, а DuckDuckGo (`html.duckduckgo.com`, без ключа) —
бесплатным каналом общего веб-поиска. Все три модуля удалены (design-
обсуждение), а не оставлены отключёнными:

- **pulscen.ru/optlist.ru** — CSS-селекторы в `config/sources.yaml` были
  `PLACEHOLDER`-заготовками с самого начала (среда разработки не имела
  сетевого доступа к этим сайтам для калибровки, см. §11) — 0 кандидатов
  всегда, не деградация, а никогда не работавший путь.
- **DuckDuckGo** — на момент написания этого раздела HTML-эндпоинт
  действительно работал без JS. Позже (проверено вживую) DuckDuckGo добавил
  антибот-защиту: `html.duckduckgo.com` теперь отдаёт JS-челлендж
  (`anomaly.js`) вместо результатов автоматическим клиентам — недоступно
  без браузера, исполняющего JavaScript, чего у прототипа нет.

Источник кандидатов по РФ сейчас — Google CSE / Yandex Search API (см.
7.1 ниже); если понадобится вернуть headless-browser-обход
антибот-защиты — см. git-историю удалённых модулей.

### 7.1 Google CSE / Yandex Search API / Yandex gen-search — общий веб-поиск

`sources/google_cse.py` (Google Custom Search JSON API) и
`sources/yandex_search.py` (Yandex Search API) — официальные API, не
скрапинг, поэтому не подвержены антибот-защите/капчам, в отличие от
удалённых источников выше. `sources/yandex_gen_search.py` — опциональный
генеративный ответ поверх того же Yandex Search API (дороже, включается
отдельным флагом). Оба класса дают не специализированный каталог с
карточками компаний, а обычную поисковую выдачу — заголовок, ссылка,
сниппет. Из этого следуют два архитектурных решения:

- **Recall, не precision.** Канал сознательно "шумный": среди результатов
  будут новости, форумы, страницы без отношения к конкретному юрлицу.
  Точность обеспечивается не на этом шаге, а резолвингом в ИНН (§10,
  `DadataEnricher`) — кандидат, не подтвердившийся в ЕГРЮЛ, остаётся
  "неподтверждённым лидом" со статусом "неизвестно", не выдаётся как
  проверенный поставщик.
- **`website` = прямая ссылка на сайт компании**, а не профиль внутри
  чужой площадки — ссылка из поисковой выдачи уже ведёт на сайт самой
  компании, что даёт дедупу (§ dedup.py) больше шансов схлопнуть один и
  тот же результат из разных источников по домену.

Общая инфраструктура (`sources/base.py`) — уважение robots.txt
(`urllib.robotparser`, кешируется по домену), rate limiting между
запросами (`config/sources.yaml`, `request_delay_seconds`), общие regex
для телефона/email/адреса как страховка там, где сниппет их содержит.

## 8. Формат выдачи и принцип «фифти-фифти»

Excel-выгрузка — не просто таблица компаний, а таблица, где **у каждого
поля есть источник, дата получения и уровень достоверности**
(`подтверждён` / `не проверен` / `протух`). Это превращает «человек
перепроверяет 50% работы» в «человек проверяет конкретные жёлтые ячейки», а
не весь список заново — иначе ИИ-инструмент не экономит время байера, а
просто добавляет шаг.

Полная цепочка верификации контакта (для e-mail/сайта) — 4 шага:
MX-запись домена → HTTP-статус сайта → сверка ИНН в футере сайта с карточкой
→ (опционально) SMTP-проверка ящика без отправки письма.

Реализован шаг 2 из 4 (`verify_contacts.py:check_website_liveness`) — HEAD-
запрос на сайт компании, результат кладётся в `Company.contacts["website"]`
с флагом `подтверждён`/`не проверен`/`протух`. Осознанно консервативная
трактовка: любой полученный HTTP-ответ (даже 403/404/503) считается "сайт
жив"; обрыв TLS-рукопожатия (`SSLError`) — "не проверен" (проверено вживую:
похоже на антибот-защиту по TLS-фингерпринту, а не на мёртвый домен —
сервер на порту реально есть, раз рукопожатие вообще началось); `протух`
ставится только на ошибку уровня соединения ДО TLS (домен не резолвится,
connection refused, таймаут). MX-запись, сверка ИНН в футере и
SMTP-проверка — не реализованы, остаются в backlog.

## 9. Критерии приёмки и как их измерить (сделать до полноценной разработки)

1. Взять 4 тестовых запроса из ТЗ (гальванические покрытия; утилизация/
   переработка отходов; лабораторные услуги; организации с лицензией).
2. Попросить байеров сделать обычный ручной ресерч по этим запросам
   **сейчас**, зафиксировать шорт-листы как golden set.
3. Прогнать те же запросы через текущий JayCopilot — зафиксировать как
   baseline.
4. Прогнать через новый пайплайн и сравнить по метрикам:
   - **recall@20** относительно golden set;
   - **precision** — доля кандидатов, подтверждённых байером как релевантные;
   - **доля «мёртвых» компаний в выдаче** — главный KPI против JayCopilot,
     напрямую отражает боль из п.2 ТЗ;
   - **полнота карточки** — % заполненных полей контактов на кандидата.
5. Без прогона п.3 нет базы для сравнения — это блокер для приёмки этапа 1,
   а не опциональный шаг.

## 10. Что реализовано в прототипе (код в `src/procurement_search/`)

Прототип реализует полный каркас пайплайна с рабочей логикой там, где она не
зависит от недоступной из среды разработки сети или платных API, и с явно
помеченными заглушками там, где зависит:

| Модуль | Статус |
|---|---|

## 11. Известные ограничения и риски прототипа

- **pulscen.ru/optlist.ru/DuckDuckGo убраны из проекта** (§7.0) — не
  ограничение, а решённый вопрос: CSS-селекторы первых двух так и остались
  неоткалиброванными PLACEHOLDER'ами (среда разработки не имела сетевого
  доступа к этим сайтам), DuckDuckGo упёрся в антибот-JS-челлендж. Реальные
  кандидаты сейчас идут только через Google CSE/Yandex Search API —
  **без хотя бы одного платного ключа поиск не находит ничего**.
- **`DadataEnricher` резолвит по названию, не по ИНН** — Dadata suggest
  принимает текстовый запрос (название компании со скрапинга), а не точный
  ИНН, поэтому для общих названий ("Ромашка", "Альфа", "Стройсервис")
  возможны ложные срабатывания. Частично компенсируется выбором того из
  топ-5 кандидатов Dadata, чей юридический адрес ближе всего к адресу со
  скрапинга (`enrichment._pick_best_suggestion`), но это эвристика, не
  гарантия. ГИР БО/ЕИС (выручка, РНП, банкротство) по-прежнему не
  подключены — `scoring.compute_scale`/`compute_reliability` остаются
  заглушками (см. ниже).
- **Полная история переименований при реорганизации не реализована** —
  `DadataEnricher` показывает ТЕКУЩЕЕ официальное название из ЕГРЮЛ (уже
  закрывает основной кейс: устаревшее имя со скрапинга заменяется актуальным),
  но не всю цепочку "было → стало". Полная история — платная выписка ЕГРЮЛ у
  Dadata, вне бесплатного тарифа.
- **Контроль актуальности контактов реализован частично** —
  `verify_contacts.py` делает только HTTP-проверку сайта (шаг 2 из 4 в §8).
  MX-запись, сверка ИНН в футере сайта и SMTP-проверка почты — не сделаны.
- **JS-рендеринг / антибот-защита по TLS-фингерпринту.** Проверено вживую
  (§7.0): скрапинг произвольных сайтов на `requests`+HTML регулярно
  упирается либо в JS-подгрузку контента (SPA/AJAX), либо в TLS-уровневую
  блокировку нероутерных клиентов (сервер видит нестандартный TLS-
  «отпечаток» и обрывает рукопожатие ещё до HTTP-ответа) — оба случая
  требуют headless-браузер (Playwright) вместо чистого HTTP-клиента, это
  отдельная задача с другим профилем рисков (антибот-детекция, капчи,
  юридическая сторона автоматизации обхода защиты).
- **Alibaba/1688/gsxt.gov.cn** в текущем прототипе не реализованы —
  предполагают заметно более серьёзную антибот-защиту, чем у уже убранных
  pulscen/optlist/DuckDuckGo (§7.0), и по-хорошему требуют отдельного
  технического решения (не просто ещё один файл `sources/alibaba.py` по
  аналогии) — вынесено за скобки этапа 1 прототипа, зафиксировано как
  открытый пункт в backlog.
- **Релевантность в скоринге сейчас примитивная** (пересечение токенов), не
  эмбеддинги — это осознанное упрощение прототипа, а не рекомендация для
  прода.

## 13. Проверка наличия и сравнение количества товара

Мотивирующий пример: закупщик пишет «генератор на бензине hunter 3000
литров 2,5 киловат 11 штук» — четыре числа в запросе, из которых только
одно (11 шт) действительно количество ЗАКУПКИ, остальные три — характеристики/
шум/индекс модели. До этого раздела `attribute_extractor.py` умел находить
пары значение+единица, но не различал их РОЛЬ: то же число могло быть и
характеристикой, которую нужно искать на сайте кандидата, и количеством,
которое искать НЕЛЬЗЯ (попадание "11" в поисковый запрос зашумляет выдачу
Yandex/Google цифрой, не относящейся к самому товару).

**Слой 0.6 — роль-классификация чисел (`attribute_extractor.classify_roles`).**
Чистый пост-процессинг уже готового результата Слоя 0 (`extract_attributes`),
без отдельного LLM-вызова: единицы измерения делятся на счётные
(шт/компл/упак/пара — кандидат в количество закупки) и физические (всё
остальное — характеристика). "Голые" числа без единицы рядом дополнительно
проверяются на маркер количества ("нужно", "требуется", "необходимо", "в
количестве") и на индекс модели (латинский бренд-токен + число без единицы,
"hunter 3000"). Одно и то же число МОЖЕТ одновременно попасть и в specs
(характеристика), и стать индексом модели — это и есть коллизия из
мотивирующего примера ("3000 литров" — специфика или огрызок "Hunter
3000"?), она не разрешается молча, а попадает в `ParsedQuery.conflicts` и
логируется байеру. Диапазоны типичности характеристик по категории товара
(`config/spec_ranges.yaml`, словарное совпадение ключевых слов, не LLM и не
`config/categories.yaml` — та таксономия для базы доверенных поставщиков,
другая по смыслу задача) дают вторую независимую причину для conflicts:
"3000 л" абсурдно для бака бензогенератора независимо от того, нашёлся ли
рядом индекс модели.

`order_qty` (найденное количество закупки) исключается из поискового
запроса дважды: (1) `search_terms[0]` строится не из `raw_query` целиком, а
из `raw_query` с вырезанным `order_qty.raw` (`pipeline.search_raw_query`) —
раньше `raw_query` всегда уходил в источники как есть, и количество закупки
утекало в поиск независимо от остальной логики; (2) `query_attributes`,
передаваемые в `scoring.has_attribute_mismatch` (Слой 0.5), тоже
фильтруются от счётных единиц — без этого "11 шт" из запроса сравнивалось
бы с ЛЮБЫМ "N шт" на сайте кандидата (артикул, фасовка, что угодно с той
же единицей) и ложно занижало бы relevance по случайному совпадению
единицы измерения, а не по смыслу характеристики товара.

**Слой 4 — наличие с числом (`availability.py`, опционально,
`--check-availability`).** Отдельная, более дорогая LLM-проверка,
параллельная уже существующему `models.StockStatus`
(`relevance_llm.classify_stock_status`) — та определяет только текстовый
статус (в наличии/уточнить/нет) без чисел, дешевле и включена по умолчанию
вместе с `--relevance-llm-check`. `check_availability` — отдельный флаг, не
завязанный на `relevance_llm_check`: обе фичи через один и тот же
LLM-провайдер (Yandex AI Studio), но с разной стоимостью вызова, смешивать
их в одном флаге запутало бы, что именно включается. Design-обсуждение:
обе проверки оставлены параллельно, а не смигрированы в одну — разный
охват (наличие без числа vs. наличие с числом/фасовкой/сроком поставки) и
разная цена оправдывают раздельные флаги.

Извлечение — единственный LLM-вызов над текстом страницы
(`yandexgpt_classifier.extract_availability_with_yandexgpt`), без лестницы
JSON-LD/CMS-шаблонов/regex из исходной постановки задачи: тот же паттерн,
что уже применён для `classify_stock_status`/`extract_price`/`extract_contacts`
в этом проекте — рунет слишком разнороден по вёрстке, чтобы покрыть его
конечным набором шаблонов, а один явный LLM-вызов дешевле в поддержке.

Отдельного шага "найти карточку товара" (internal search/sitemap.xml, как
в исходной постановке задачи) не строится — находка, сделанная при
проектировании: `Candidate.website` в обоих активных источниках
(`sources/google_cse.py`, `sources/yandex_search.py`) — это буквально URL,
который нашёлся В ПОИСКЕ (не хардкод на главную страницу сайта), и
`site_relevance.crawl_site_text` уже качает именно его первым, сохраняя
путь. Значит текст, который Слой 2 уже скачал для проверки relevance/цены
(`_refine_relevance`), в большинстве случаев уже и есть текст карточки
конкретного товара — `availability.py` просто переиспользует его, без
дополнительных HTTP-запросов.

**Сравнение количества (`quantity_match.py`).** Чистая функция без сети/LLM:
сравнивает `order_qty` с найденным `Availability.quantity`, с явным
приведением единиц через фасовку (`Availability.pack_size` — "2 упаковки"
пересчитываются в штуки, только если известно, сколько штук в упаковке;
без этого — `UNIT_MISMATCH`, а не молчаливое приведение и не `NOT_ENOUGH`).
Семь исходов (`Verdict`) сортируются НЕ по бинарному "подходит/не подходит":
поставщик с частичным остатком ("10 из 11") — более действенная зацепка
для байера (звонок и довоз — рабочий сценарий), чем полное отсутствие
данных, поэтому `NOT_ENOUGH` ранжируется выше `UNKNOWN`
(`VERDICT_SORT_ORDER`, применяется в `pipeline._ranking_key`). ГЛАВНЫЙ
уровень сортировки — цена (байер явно попросил именно так, см. докстринг
`_ranking_key`: пробовали поднять вердикт наличия ВЫШЕ цены — на живой
выдаче это давало странный результат, дорогая позиция с найденным
остатком обгоняла заметно более дешёвую без данных об остатке, откачено);
вердикт наличия — тай-брейк внутри ОДИНАКОВОЙ цены, а не общий приоритет.
Единственный исход, который выкидывает поставщика из выдачи целиком —
`OUT_OF_STOCK` (тот же knockout-паттерн и то же обязательное логирование,
что и у ЕГРЮЛ-отсечки в `pipeline._is_knockout`): показывать байеру
заведомо нерабочего поставщика бессмысленно, в отличие от
`NOT_ENOUGH`/`UNKNOWN`, где уточнение по телефону всё ещё работает.

`UNKNOWN` (наличие не опубликовано на сайте — типичный случай для
большинства поставщиков) намеренно НЕ штрафуется — тот же принцип "нет
данных — не штраф", что и везде в `scoring.py`/`attribute_extractor.py`.
При этом сам факт ПРОВЕРКИ учитывается в `compute_confidence`
(`company.availability is not None` — присутствие попытки, не качество
результата: `UNKNOWN` при реально отработавшем LLM-вызове всё равно
засчитывается как "поле заполнено", штрафуется только полное отсутствие
попытки).

### 13.1. Метраж закупки (order_length) — параллельно order_qty

Не всякий товар считается штуками — кабель, трубы, шланги, ткань продаются
на отрез, запрос про них выглядит как "нужно 50 метров кабеля ВВГ" или
"кабель ВВГ 3х2,5 500 метров", а не "N штук". `ParsedQuery` (см.
`attribute_extractor.classify_roles`) получил второе, независимое от
`order_qty` поле — `order_length` — с той же ролью "сколько закупить",
только в единицах длины (`LENGTH_UNITS`: м/мм/см/км), а не в счётных
единицах (`COUNT_UNITS`).

Разделение specs/order_length эвристическое (единого правила "единица
длины = метраж" быть не может — длина легитимно бывает и характеристикой
ОДНОГО экземпляра, например "труба 1.5 метра, 20 штук"):
1. Явный маркер количества ("нужно", "требуется" — тот же список, что и у
   order_qty) рядом с конкретным вхождением длины — побеждает независимо
   от остального.
2. Без маркера — единственная во всём запросе величина длины, при
   ОТСУТСТВИИ `order_qty` (счётного количества) — тоже считается метражом
   закупки. Как только `order_qty` уже найден (типовой случай "труба 1.5
   метра, 20 штук") — длина остаётся характеристикой, не становится
   `order_length`: 1.5 метра здесь — длина одной трубы, а не то, сколько
   метров нужно купить.
3. Несколько длин с маркером одновременно, или несколько длин без
   маркера — неоднозначность попадает в `conflicts`/остаётся в `specs`
   соответственно, не разрешается молча (тот же принцип, что у коллизии
   model/specs в §13).

`order_qty` и `order_length` — РАВНОПРАВНЫЕ, не одно и то же поле "на
выбор": оба могут быть заполнены одновременно (каждый со своим явным
маркером, "нужно 6 комплектов, требуется 50 метров кабеля к ним"). Везде,
где пайплайну нужна ОДНА цель для сравнения с остатком на сайте кандидата
(Слой 4, экспорт, сводка `summarize_availability`) —
`pipeline._effective_order_amount`/`SearchResult.effective_order_amount()`
выбирают `order_qty`, если он найден, иначе `order_length`; это чисто
исторический приоритет (order_qty появился в проекте первым), не
содержательное преимущество одной единицы над другой.

Ключевая архитектурная находка: `quantity_match.compare()` и
`Availability.quantity` уже были общими по единице измерения с самого
начала (`Quantity(value, unit, raw)` — `unit` произвольная строка, не
фиксированный enum) — сравнение остатка "300 метров в наличии" с "нужно
500 метров" работает той же функцией, что и "15 шт в наличии" vs "нужно
11 шт", без единой строчки изменений в `quantity_match.py`. Только
`pipeline.py` нужно было научить выбирать, КАКОЕ из двух полей запроса
передать в сравнение — сама механика сравнения оказалась изначально
безразличной к единице измерения. `stepper_probe.py` по той же причине тоже не потребовал
изменений: клик по "+" не знает и не обязан знать, штуки он считает или
метры, работает с голым числом в поле ввода.

## 14. Интерактивная проверка остатка через степпер количества (пилот)

Мотивация: на живой выдаче подавляющее большинство карточек товара НЕ
публикуют точное число в тексте («в наличии», без цифры) — Слой 4
(`extract_availability`, LLM над статичным текстом) честно возвращает
`UNKNOWN`/`IN_STOCK_NO_QTY`, потому что цифры действительно нет в HTML.
Но у многих магазинов число всё-таки СУЩЕСТВУЕТ — оно просто не в тексте,
а в поведении JS-виджета количества («−  1  +»): попытка добавить в
корзину больше, чем есть на складе, часто либо показывает ошибку, либо
просто не даёт числу расти дальше. Это сигнал, принципиально невидимый
чистому HTTP-краулингу (`site_relevance.crawl_site_text` — `requests`,
без исполнения JS).

**`stepper_probe.py`** — единственное место в проекте, где вместо
HTTP-текста + LLM используется headless-браузер (Playwright): открывает
уже найденный поиском URL и кликает по «+» (или считывает остановку роста
значения поля) до `order_qty` включительно. Ничего не покупает, не
отправляет форм — только клики по степперу и чтение DOM.

Осознанно узкий пилот, а не постоянная часть пайплайна:
- Отдельный флаг `probe_stepper` (`--probe-stepper`/чекбокс в UI),
  выключен по умолчанию, требует `check_availability=True` — запускается
  ТОЛЬКО для кандидатов с уже неясным вердиктом Слоя 4
  (`_STEPPER_PROBE_ELIGIBLE_VERDICTS`: `UNKNOWN`/`NOT_ENOUGH`/
  `IN_STOCK_NO_QTY`), не тратится там, где LLM уже дала уверенный ответ.
- `playwright` — НЕ в `requirements.txt` (тяжёлая опциональная
  зависимость, ~275 МБ с браузерным бинарником, отдельный шаг установки
  `playwright install chromium` после `pip install`). Отсутствие пакета —
  не ошибка, а тихий no-op с предупреждением в лог (тот же принцип
  graceful degradation, что у остальных опциональных возможностей
  проекта).
- Один браузер на весь `search_and_score` (не по экземпляру на
  кандидата — запуск Chromium сам по себе стоит секунды).

**Эвристика, не гарантия** — то же предупреждение, что и у остальных
LLM/regex-извлечений в проекте, только острее: единой вёрстки степпера не
существует (искали "+"-подобный элемент, поле количества берётся как
сосед по DOM — работает на многих сайтах, но не на всех), и часть
магазинов вообще не проверяет остаток на фронте (пускают вбить любое
число, отклоняют только на checkout) — в этом случае `target_confirmed=True`
означает не "остатка гарантированно хватит", а "сайт не сказал обратного".
Отсутствие результата (`None` — степпер не найден/страница не открылась)
не трогает вердикт Слоя 4, не штрафует.

**Двухшаговая эвристика** (`_try_add_to_cart_then_find_stepper`) — добавлена
по факту на живой выдаче: 7 из 7 кандидатов подряд ответили "степпер не
найден" при первой же проверке — слишком системно для случайности.
Причина — распространённый двухшаговый UX, у которого степпера
количества физически НЕТ в исходном DOM: сначала одна кнопка "Купить"/
"В корзину", JS дорисовывает степпер только ПОСЛЕ клика по ней. Второй
шаг эвристики кликает по такой кнопке один раз и ищет степпер заново.
Безопасность: если клик увёл на другую страницу (URL изменился —
признак "оформить заказ", а не "положить в корзину на месте") — сразу
`None`, не продолжаем работать на чужой странице; дальше одного клика
ничего не идёт — корзина не открывается, заказ не оформляется, формы не
отправляются.

**Третий шаг — LLM-подсказка** (`_try_llm_guided_click_then_find_stepper`,
design-обсуждение: явный запрос пользователя "прокликать кнопки, а если
не получилось — браузерный агент", БЕЗ реестра адаптеров/replay
внутренних API/автозаказов — это осознанно отклонённая часть более
широкого плана, см. обсуждение). Последний и самый дорогой шаг: когда
шаги 1-2 (фиксированные селекторы) не сработали, YandexGPT (та же
инфраструктура, что и везде в проекте — `yandexgpt_classifier.py`,
`locate_cart_control_with_yandexgpt`) получает пронумерованный ТЕКСТОВЫЙ
список кликабельных элементов страницы (тег + видимый текст — не
скриншот, YandexGPT в этом проекте не мультимодальная) и сама выбирает
индекс элемента, похожего на "+"/"в корзину"; `null`, если ничего явно
не подходит — не угадывает клик наугад. Тот же принцип защиты от
навигации, что и в шаге 2. Требует уже включённого LLM-провайдера
(`check_availability`) — при недоступном ключе/пакете шаг молча
пропускается, шаги 1-2 остаются рабочими без LLM вовсе.

Открытый вопрос для расширения пилота за пределы узкой проверки: стоит ли
инвестировать в headless-браузер шире (замену `crawl_site_text` целиком)
ради обхода антибот-защиты по TLS-фингерпринту (см. §11) — отдельная,
более дорогая задача, не решается этим пилотом (пилот открывает браузер
уже на успешно найденном URL, не решает проблему заблокированных
доменов).
