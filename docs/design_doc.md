# Технический дизайн-документ: ИИ-поиск поставщиков (Direct Procurement)

Версия: 0.1 (черновик для пилота, этап 1)
Дата: 2026-08-06
Статус: draft — требует согласования с бизнес-заказчиком закупок и владельцем данных

## 1. Резюме

Задача по ТЗ — не «ИИ, который гуглит поставщиков», а система, которая
превращает текстовый запрос байера в проверяемый структурированный список
кандидатов. Ключевая архитектурная развилка: там, где JayCopilot полагается
на LLM «из головы» (отсюда галлюцинации, мёртвые компании, нестабильная
глубина), это решение строится как **пайплайн с детерминированным ядром и
LLM только на краях** — нормализация запроса и извлечение фактов из текста.
LLM никогда не является источником факта о компании; источник факта — это
реестр, сайт компании или площадка, а LLM в лучшем случае помогает его найти
или прочитать.

Главный принцип верификации: **любой кандидат либо резолвится в ИНН
(ОГРН), либо остаётся лидом**, а не поставщиком. Это закрывает три болевые
точки из ТЗ одним механизмом: прекращение деятельности, смена названия/
реорганизация, актуальность контактов — всё это факты, привязанные к ИНН, а
не к строке текста.

## 2. Из ТЗ в архитектуру: таблица трассируемости

| Требование ТЗ | Как закрывается |
|---|---|
| Поиск по РФ | pulscen.ru + optlist.ru (обязательные) + общий веб-поиск через DuckDuckGo (см. §7) |
| Поиск по зарубежью (Китай, Alibaba и т.п.) | Отдельный канал generate_candidates для зарубежных источников (см. §7) — не реализован в этапе 1 |
| Карточка поставщика (контакты, сводка) | Enrichment-слой, факты с указанием источника и даты |
| Весовые критерии / ранжирование | Детерминированный скоринг (§6), веса — конфиг, не хардкод |
| Отсев неактуальных / сменивших имя | Резолвинг в ИНН через `DadataEnricher` (реализовано, см. §10) + жёсткое исключение ликвидированных из выдачи в `pipeline.py` |
| Работа с реестрами (лицензии, Роспотребнадзор) | Enrichment по категориям (§5.4); Росреестр — см. примечание ниже |
| Excel-выдача | Export-слой с полями "источник/дата/достоверность" на каждое значение |
| Сверка с ручным ресерчем, KPI | Golden set + метрики (§9) |
| «Фифти-фифти» (человек проверяет) | Флаги достоверности на уровне поля, не всей записи (§8) |
| Тиражируемость на другие категории | Категория = конфиг маппинга "текст → коды/источники", не новый код (§4) |

**Примечание по Росреестру.** Росреестр — реестр объектов недвижимости и
прав на них, он не предназначен для проверки юрлиц-поставщиков. Скорее
всего попал в ТЗ по инерции («реестр = проверка контрагента»). Рекомендация:
заменить на ГИР БО (bo.nalog.ru, финансовая отчётность) и ЕИС zakupki.gov.ru
(история контрактов, РНП) — они закрывают реальную потребность в проверке
надёжности. Если у Росреестра всё же есть конкретный кейс использования
(например, проверка юр. адреса на массовость через объект недвижимости),
это нужно явно сформулировать с заказчиком отдельным пунктом.

## 3. Пайплайн (по шагам)

```
Запрос байера
     │
     ▼
[1] Нормализация запроса (LLM + справочник)
     │  → термины, синонимы, ОКВЭД/ТН ВЭД, категория пилота
     ▼
[2] Генерация кандидатов (recall, широкий охват)
     │  ├─ pulscen.ru (обязательный источник)
     │  ├─ optlist.ru (обязательный источник)
     │  ├─ веб-поиск (общий) — DuckDuckGo, реализовано (§7.1)
     │  ├─ Локальная база ЕГРЮЛ (BM25 + эмбеддинги) — не реализовано
     │  └─ зарубежные источники (Alibaba/1688/gsxt.gov.cn и т.п.) — не реализовано
     ▼
[3] Резолвинг в ИНН/ОГРН (precision)
     │  → отсев ликвидированных/банкротных/недостоверных
     │  → нерезолвленные кандидаты уходят в корзину "неподтверждённые лиды"
     ▼
[4] Обогащение фактами (по ИНН, по источникам §5)
     ▼
[5] Дедупликация и слияние карточек (несколько источников → одна компания)
     ▼
[6] Скоринг (релевантность / масштаб / надёжность)
     ▼
[7] Экспорт в Excel с полями "источник/дата/достоверность"
```

Каждый шаг — отдельный модуль с логами и метриками, чтобы можно было мерить
recall/precision по шагам, а не только итоговое качество (см. §9).

## 4. Тиражируемость: конфиг категории закупки

Новая категория закупок = новая запись в `config/categories.yaml`, а не
новый код:

```yaml
Гальванические_покрытия:
  synonyms: [анодирование, цинкование, хромирование, никелирование, "гальваника"]
  okved: ["25.61"]
  tnved: ["7419", "7616"]
  registries: []          # спецреестров не требует

Утилизация_отходов:
  synonyms: ["переработка отходов", "вывоз отходов", "обращение с отходами"]
  okved: ["38.11", "38.21", "38.32"]
  registries: [rpn_waste_license]   # реестр лицензий Росприроднадзора

Лабораторные_услуги:
  synonyms: ["испытательная лаборатория", "аккредитованная лаборатория"]
  okved: ["71.20"]
  registries: [rosakkreditatsiya, roszdravnadzor]
```

Пилот по 4 тестовым запросам из ТЗ должен зафиксировать этот формат так,
чтобы категорийный менеджер мог сам добавлять новые категории без участия
разработчиков.

## 5. Источники данных

### 5.1 Ядро (обязательные)

- **ЕГРЮЛ/ЕГРИП** (открытые данные ФНС, egrul.nalog.ru) — статус компании,
  ИНН/ОГРН, юр. адрес, история наименований, правопреемство при
  реорганизации, дисквалификация руководителей.
- **pulscen.ru** — обязательный источник кандидатов и части контактных
  данных (см. §7 про парсинг).
- **optlist.ru** — обязательный источник кандидатов, преимущественно
  опт/B2B-предложения (см. §7).

### 5.2 Финансы и масштаб

- **ГИР БО** (bo.nalog.ru) — бухгалтерская отчётность, закрывает требование
  «оборот за последние ~2 года» напрямую и бесплатно.
- Численность сотрудников — открытые данные ФНС (среднесписочная
  численность) либо коммерческие агрегаторы (см. 5.5).

### 5.3 Надёжность

- **ЕИС zakupki.gov.ru** — история контрактов, реестр недобросовестных
  поставщиков (РНП).
- **КАД Арбитр** — арбитражные споры.
- **ФССП** — исполнительные производства.
- **Федресурс / ЕФРСБ** — банкротство, существенные факты.
- Налоговая задолженность — открытые данные ФНС.

### 5.4 Отраслевые реестры (по категории, из `registries` в конфиге)

- Утилизация отходов → реестр лицензий Росприроднадзора (I–IV класс
  опасности).
- Лабораторные услуги → реестр аккредитованных лиц Росаккредитации
  (**с проверкой области аккредитации**, а не только факта наличия
  аккредитации), Росздравнадзор — для медицинских лабораторий.
- Прочие лицензируемые виды деятельности → ФГИС «Реестр лицензий»,
  Ростехнадзор — по необходимости.

### 5.5 Быстрый старт / зарубежье

- **Dadata** — реализовано (`enrichment.DadataEnricher`, см. §10): бесплатный
  тариф suggest API по названию организации для старта пилота, прежде чем
  вкладываться в полноценный локальный индекс ЕГРЮЛ. Есть дневной лимит
  бесплатных запросов (порядок — тысячи в день, уточнить текущий на
  dadata.ru при выходе за пилот).
- Далее, по мере роста нагрузки — Контур.Фокус / СПАРК / Seldon.Basis.
- Зарубежье: **gsxt.gov.cn** (китайский госреестр юрлиц, аналог ЕГРЮЛ),
  OpenCorporates, GLEIF (LEI). Alibaba/Made-in-China/1688 — открытого
  поискового API нет, нужен парсинг с учётом их anti-bot защиты (это на
  порядок сложнее pulscen/optlist — см. риски в §11). Опционально:
  ImportYeti / Panjiva / ImportGenius (таможенные декларации) — сильный
  сигнал, что поставщик реально отгружает товар, а не просто зарегистрирован
  на площадке.

## 6. Скоринг

LLM не используется для оценки «надёжность от 1 до 10» — такая оценка не
воспроизводима и не объяснима. Вместо этого — детерминированная формула из
фактов плюс отдельный LLM-скор релевантности текста запроса к номенклатуре
кандидата.

| Ось | Из чего считается | Источник |
|---|---|---|
| Релевантность | совпадение ОКВЭД/ТН ВЭД, семантическое сходство запроса с описанием/номенклатурой на сайте или в карточке маркетплейса | ЕГРЮЛ (ОКВЭД) + текст карточки |
| Масштаб / серьёзность | выручка, численность сотрудников, срок существования, размер УК | ГИР БО, ФНС |
| Надёжность | наличие в РНП, банкротство, открытые исполнительные производства, налоговая задолженность, отметка о недостоверности сведений в ЕГРЮЛ | ЕИС, Федресурс, ФССП, ФНС |

Итоговый скор — взвешенная сумма нормализованных (0..1) осей, веса — в
`config/scoring_weights.yaml`, отдельный набор весов на категорию (для
лабораторных услуг наличие аккредитации может быть отсекающим фильтром, а
не просто весом).

В прототипе (см. §10) реализован только каркас формулы и релевантность по
пересечению текстовых токенов — интеграция с ЕГРЮЛ/ГИР БО/ЕИС вынесена как
`Enricher`-интерфейс, который сейчас реализован заглушкой (нет доступа к
платным API/сети из среды разработки, см. §11).

## 7. Обязательные источники pulscen.ru и optlist.ru — как парсим

Технически оба источника — генераторы **кандидатов** (шаг [2] пайплайна),
не источники истины: любой факт, полученный отсюда, вторичен по отношению к
резолвингу в ЕГРЮЛ на шаге [3]. Практическая причина: у B2B-каталогов нет
гарантии, что карточка компании актуальна (протухшие объявления, компании,
переставшие отвечать) — это именно та проблема, которую ТЗ просит решить, а
не унаследовать.

Архитектура парсера одинакова для обоих сайтов (`sources/pulscen.py`,
`sources/optlist.py`, общий интерфейс в `sources/base.py`):

1. **Извлечение через structured data (приоритет).** Большинство
   каталогов такого типа размечают карточки организаций через
   `schema.org` (JSON-LD `Organization`/`LocalBusiness`/`Product` или
   microdata) в SEO-целях. Это самый устойчивый способ парсинга — не ломается
   при рестайле вёрстки. Реализовано в `sources/base.py:extract_jsonld`.
2. **Fallback на CSS-селекторы.** Если разметки нет, используются
   селекторы из `config/sources.yaml`. Они помечены как `PLACEHOLDER` и
   требуют калибровки (см. `README.md`, раздел «Калибровка селекторов») —
   среда разработки, где писался этот прототип, не имеет сетевого доступа к
   pulscen.ru и optlist.ru (см. §11), поэтому точные классы/атрибуты не
   верифицированы вживую.
3. **Извлечение телефона/email regex-ом** из полученного текста как
   дополнительная страховка, если основной путь не нашёл контакт (некоторые
   такие каталоги показывают телефон только по клику/JS — тогда регулярка на
   статичный HTML ничего не даст, и это отдельный риск, см. §11).
4. **Уважение robots.txt** — `sources/base.py` проверяет правила через
   `urllib.robotparser` перед первым запросом к домену и кеширует результат.
5. **Rate limiting** — задержка между запросами настраивается в
   `config/sources.yaml` (`request_delay_seconds`), по умолчанию
   консервативная, чтобы не создавать нагрузку на чужой сервис.

### 7.1 Расширение за пределы 2 сайтов: DuckDuckGo (общий веб-поиск)

Реализовано в `sources/duckduckgo.py`. В отличие от pulscen/optlist это не
специализированный каталог с карточками компаний, а обычная поисковая
выдача — заголовок, ссылка, сниппет. Из этого следуют два архитектурных
решения:

- **Recall, не precision.** Канал сознательно "шумный": среди результатов
  будут новости, форумы, страницы без отношения к конкретному юрлицу.
  Точность обеспечивается не на этом шаге, а резолвингом в ИНН (§10,
  `DadataEnricher`) — кандидат, не подтвердившийся в ЕГРЮЛ, остаётся
  "неподтверждённым лидом" со статусом "неизвестно", не выдаётся как
  проверенный поставщик.
- **`website` = прямая ссылка, а не профиль каталога.** У pulscen/optlist
  `source_url` обычно указывает на страницу внутри самой площадки — поэтому
  там `website` кандидата чаще всего `None` (см. `models.Candidate`). У
  DuckDuckGo ссылка из выдачи уже ведёт на сайт самой компании — значит,
  `website` заполняется всегда, что даёт дедупу (§ dedup.py) больше шансов
  схлопнуть один и тот же результат из разных источников по домену.

Технически — HTML-версия DuckDuckGo (`html.duckduckgo.com`, без JS и без
API-ключа), с тем же уважением robots.txt/rate limiting, что и у остальных
источников (общая инфраструктура `sources/base.py:fetch_url`). Важная
оговорка: автоматизированный сбор формально не разрешён пользовательским
соглашением DuckDuckGo — компенсируется низкой частотой запросов и
соблюдением robots.txt, но это не индульгенция, а осознанный компромисс
для прототипа; при переходе в пилот с заметным объёмом стоит рассмотреть
платный Bing/Google Custom Search API как более устойчивую альтернативу.

## 8. Формат выдачи и принцип «фифти-фифти»

Excel-выгрузка — не просто таблица компаний, а таблица, где **у каждого
поля есть источник, дата получения и уровень достоверности**
(`подтверждён` / `не проверен` / `протух`). Это превращает «человек
перепроверяет 50% работы» в «человек проверяет конкретные жёлтые ячейки», а
не весь список заново — иначе ИИ-инструмент не экономит время байера, а
просто добавляет шаг.

Полная цепочка верификации контакта (для e-mail/сайта) — 4 шага:
MX-запись домена → HTTP-статус сайта → сверка ИНН в футере сайта с карточкой
→ (опционально) SMTP-проверка ящика без отправки письма.

Реализован шаг 2 из 4 (`verify_contacts.py:check_website_liveness`) — HEAD-
запрос на сайт компании, результат кладётся в `Company.contacts["website"]`
с флагом `подтверждён`/`протух`. Осознанно консервативная трактовка: любой
полученный HTTP-ответ (даже 403/404/503) считается "сайт жив", `протух`
ставится только на ошибку уровня соединения (домен не резолвится, connection
refused, таймаут) — иначе антибот-блокировка (см. риски по pulscen/optlist)
ошибочно читалась бы как "компания прекратила существование". MX-запись,
сверка ИНН в футере и SMTP-проверка — не реализованы, остаются в backlog.

## 9. Критерии приёмки и как их измерить (сделать до полноценной разработки)

1. Взять 4 тестовых запроса из ТЗ (гальванические покрытия; утилизация/
   переработка отходов; лабораторные услуги; организации с лицензией).
2. Попросить байеров сделать обычный ручной ресерч по этим запросам
   **сейчас**, зафиксировать шорт-листы как golden set.
3. Прогнать те же запросы через текущий JayCopilot — зафиксировать как
   baseline.
4. Прогнать через новый пайплайн и сравнить по метрикам:
   - **recall@20** относительно golden set;
   - **precision** — доля кандидатов, подтверждённых байером как релевантные;
   - **доля «мёртвых» компаний в выдаче** — главный KPI против JayCopilot,
     напрямую отражает боль из п.2 ТЗ;
   - **полнота карточки** — % заполненных полей контактов на кандидата.
5. Без прогона п.3 нет базы для сравнения — это блокер для приёмки этапа 1,
   а не опциональный шаг.

## 10. Что реализовано в прототипе (код в `src/procurement_search/`)

Прототип реализует полный каркас пайплайна с рабочей логикой там, где она не
зависит от недоступной из среды разработки сети или платных API, и с явно
помеченными заглушками там, где зависит:

| Модуль | Статус |
|---|---|
| `query_normalizer.py` | Рабочий — маппинг запрос → синонимы/ОКВЭД из `config/categories.yaml`; опциональный LLM-fallback на случай, если словарь не нашёл совпадений — `llm_classifier.py` (Anthropic SDK, платный) или `ollama_classifier.py` (локальная модель, бесплатно; выбор через `LLM_PROVIDER`). Выключен по умолчанию (`use_llm_fallback=False`) |
| `sources/pulscen.py`, `sources/optlist.py` | Рабочий парсер (JSON-LD + CSS fallback), **селекторы требуют калибровки** — см. §11 |
| `sources/duckduckgo.py` | Рабочий — общий веб-поиск, канал "весь интернет" (§7.1), бесплатно, без ключа |
| `dedup.py` | Рабочий — нормализация имени/телефона/домена, слияние дублей |
| `enrichment.py` | `NullEnricher` (честная заглушка) **и** `DadataEnricher` (рабочая интеграция с Dadata suggest API): резолвинг в ИНН/ОГРН, статус из ЕГРЮЛ, официальное название заменяет устаревшее со скрапинга при смене названия/реорганизации. Матчинг по имени — эвристика (топ-5 кандидатов Dadata, выбор по пересечению адреса), не гарантия точного резолвинга — см. §11 |
| `verify_contacts.py` | Рабочий — HTTP-проверка живости сайта компании (шаг 2 из 4 в §8), результат в `Company.contacts["website"]` |
| `scoring.py` | Рабочая формула, релевантность — по пересечению токенов (заглушка вместо эмбеддингов/LLM) |
| `export.py` | Рабочий — Excel с полями источник/дата/достоверность, включая колонку "Сайт" |
| `pipeline.py` | Рабочий — связывает всё, **жёстко исключает ликвидированные компании** из финальной выдачи (`DEAD_COMPANY_STATUSES`, ТЗ п.4) |
| `cli.py`, `webapp.py` + `static/index.html` | Рабочий — CLI-команда и локальный веб-GUI (FastAPI + ванильный JS) поверх одного и того же пайплайна |

## 11. Известные ограничения и риски прототипа

- **Нет сетевого доступа к pulscen.ru/optlist.ru из среды, где писался этот
  код.** Оба домена недоступны (DNS резолвится в заблокированный адрес).
  CSS-селекторы в `config/sources.yaml` — лучшее предположение по типовой
  вёрстке подобных каталогов, **не проверены на реальных страницах**. Перед
  использованием в проде обязательно откалибровать их через DevTools на
  живых страницах (пошагово в `README.md`).
- **`DadataEnricher` резолвит по названию, не по ИНН** — Dadata suggest
  принимает текстовый запрос (название компании со скрапинга), а не точный
  ИНН, поэтому для общих названий ("Ромашка", "Альфа", "Стройсервис")
  возможны ложные срабатывания. Частично компенсируется выбором того из
  топ-5 кандидатов Dadata, чей юридический адрес ближе всего к адресу со
  скрапинга (`enrichment._pick_best_suggestion`), но это эвристика, не
  гарантия. ГИР БО/ЕИС (выручка, РНП, банкротство) по-прежнему не
  подключены — `scoring.compute_scale`/`compute_reliability` остаются
  заглушками (см. ниже).
- **Полная история переименований при реорганизации не реализована** —
  `DadataEnricher` показывает ТЕКУЩЕЕ официальное название из ЕГРЮЛ (уже
  закрывает основной кейс: устаревшее имя со скрапинга заменяется актуальным),
  но не всю цепочку "было → стало". Полная история — платная выписка ЕГРЮЛ у
  Dadata, вне бесплатного тарифа.
- **Контроль актуальности контактов реализован частично** —
  `verify_contacts.py` делает только HTTP-проверку сайта (шаг 2 из 4 в §8).
  MX-запись, сверка ИНН в футере сайта и SMTP-проверка почты — не сделаны.
- **JS-рендеринг.** Если pulscen.ru/optlist.ru подгружают карточки или
  телефоны через JavaScript (SPA/AJAX-подгрузка, антибот-защита телефона по
  клику), парсер на `requests`+HTML не увидит эти данные — потребуется
  headless-браузер (Playwright), это отдельная задача с другим профилем
  рисков (антибот-детекция, капчи, юридическая сторона автоматизации
  обхода защиты). Уточнить у заказчика после первой калибровки.
- **Alibaba/1688/gsxt.gov.cn** в текущем прототипе не реализованы —
  предполагают заметно более серьёзную антибот-защиту, чем pulscen/optlist,
  и по-хорошему требуют отдельного технического решения (не просто ещё один
  файл `sources/alibaba.py` по аналогии) — вынесено за скобки этапа 1
  прототипа, зафиксировано как открытый пункт в backlog.
- **Релевантность в скоринге сейчас примитивная** (пересечение токенов), не
  эмбеддинги — это осознанное упрощение прототипа, а не рекомендация для
  прода.

## 12. Открытые вопросы к бизнесу (нужно решить до пилота)

1. Росреестр — какой конкретно сценарий использования подразумевался?
   Если это про проверку юр. адреса на «массовость» — стоит явно
   сформулировать, иначе предлагается замена на ГИР БО + ЕИС (см. §2).
2. Нужен ли headless-браузер для pulscen/optlist (зависит от того,
   прячут ли они телефоны за JS) — уточняется на этапе калибровки
   селекторов, но бюджет/сроки лучше согласовать заранее.
3. Источник финансирования доступа к платным реестрам (СПАРК/Контур.Фокус)
   после пилота на Dadata — кто согласовывает.
4. Правовая позиция по автоматизированному парсингу зарубежных агрегаторов
   (Alibaba и т.п.) — обычно требует отдельного review, ToS этих площадок
   часто прямо запрещают автоматический сбор данных.
5. Бюджет на переход с бесплатного тарифа Dadata на платный (или на
   Контур.Фокус/СПАРК) — когда дневной лимит бесплатных suggest-запросов
   станет узким местом при росте объёма пилота.
6. Стоит ли инвестировать в оставшиеся 2 шага верификации контактов из 4
   (MX-запись, сверка ИНН в футере сайта, SMTP-проверка) — сейчас сделан
   только HTTP-статус сайта (§8); решение зависит от того, насколько часто
   "живой сайт, но протухший email" оказывается проблемой на практике.
7. Правовая позиция по автоматизированному использованию DuckDuckGo
   (§7.1) — пользовательское соглашение формально не разрешает
   автоматизированный сбор; для пилота с заметным объёмом стоит рассмотреть
   платный Bing/Google Custom Search API как более устойчивую замену.
